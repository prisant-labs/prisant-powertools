## Purpose

Enable structured cross-LLM peer review of plans, briefs, specs, and other documents by generating a self-contained review request that a second LLM can complete independently, then synthesizing the findings back into actionable decisions. This addresses the gap where single-LLM review produces echo-chamber feedback. [S1, S2]

## Scope

### In Scope

- Two modes: `--review` (generate request) and `--respond` (synthesize findings)
- Five document types with type-specific review dimensions
- Severity framework for findings
- Self-contained output that the reviewer LLM can act on without additional context
- Bidirectional file naming convention so source and review remain linked
- Anti-sycophancy instructions baked into reviewer-facing template

### Non-Goals

- Auto-invoking the second LLM (user copies output to reviewer LLM manually)
- Tracking review history beyond the immediate file
- Generating reviews of code (this is for documents, not code)
- Multi-round reviews (one round only; subsequent rounds re-invoke the skill)
- Comparing outputs from multiple reviewer LLMs (single reviewer per invocation)

## Users / Actors

| Actor | Role | Interaction |
|-------|------|-------------|
| Requestor LLM (Claude) | Generates the review request and later synthesizes findings | Invokes the skill in `--review` mode, then later in `--respond` mode |
| Reviewer LLM (Codex / GPT / Gemini) | Reads the review request, writes findings into the template | Reads the file generated by `--review`; fills it in; returns to user |
| User (JP) | Orchestrates the handoff between LLMs | Copies output between Claude session and reviewer LLM session |

## Requirements

1. The skill must produce documents that the reviewer LLM can act on with zero additional context - every required reference is embedded or summarized in the file. [S1]
2. The `--respond` mode must scale response detail to severity: full paragraphs for Blocker / Major findings; one-liners for Minor / Note. [S2]
3. Anti-sycophancy guidance is mandatory in the reviewer-facing template - disagreement is more valuable than agreement, and the reviewer is instructed to look harder if they find nothing wrong. [S1, S3]
4. Output file naming is `<basename>_reviewed-by-<reviewer>.md` so the relationship to the source document is mechanically discoverable. [S2]
5. Document type detection is automatic from filename and content; user can override with `--type`. [S2]

## Acceptance Criteria

AC-1: In `--review` mode, skill produces a self-contained file at `<basename>_reviewed-by-<reviewer>.md` containing reviewer instructions, source context, severity framework, and template placeholders. [S1, S2]

AC-2: In `--respond` mode, skill reads the reviewer's filled findings and produces requestor synthesis with inline responses, structured decisions, and a Proposed Actions table. [S2]
  Given: a `<basename>_reviewed-by-<reviewer>.md` with completed reviewer findings
  When: skill runs in `--respond` mode
  Then: file is updated with Reviewer Assessment summary, Requestor Analysis, per-section responses scaled by severity, and a consolidated actions table

AC-3: Skill supports document types: `plan`, `brief`, `spec` (alias `prd`), `rfc`, `doc` (generic). Each type has 5-7 review dimensions. Type is auto-detected unless `--type` is passed. [S2]

AC-4: Reviewer template includes anti-sycophancy instructions: "Disagreement is more valuable than agreement", "If you find nothing wrong, look harder", "Cite specific evidence for every finding". [S1, S3]

AC-5: Output file naming follows `<basename>_reviewed-by-<reviewer>.md`. Reviewer must be one of: codex, gpt, gemini, claude, generic. [S2]

AC-6: Severity framework with four levels - Blocker / Major / Minor / Note - appears in every review request, with definitions. [S2]

AC-7: When source document exceeds 200 lines, skill summarizes key claims (3-5 bullets) plus a path reference, rather than embedding the full document. [S2]
  Given: a source document of 350 lines
  When: skill runs in `--review` mode
  Then: review file's "Document Under Review" section contains "Key claims to validate:" with 3-5 bullets and `Source: <path>` rather than the full 350 lines

## Notes on This Example

- **`status: committed` mid-spec.** AC fulfillment is happening; the spec itself is frozen. New AC discoveries would require a Revisions entry.
- **Mid-implementation Task Summary.** Three AC ticked with PR references. One AC currently in-progress with claimant. Open Questions count > 0.
- **One `[model-inference]`.** Latency NFR isn't yet measured; honest about it. `requires-human-review` is `false` because the inference is contained to one NFR with low risk; if multiple AC were inferred, set `true`.
- **Revisions has 3 entries.** Initial creation, namespace rename (clarification - no behavior change), promotion to committed. Notice the type column distinguishes these.
- **Multiple sources, mixed credibility.** S1, S2, S3 are class A (project-internal). S4 is class B (external precedent). Acceptable mix.
- **Open Questions are real questions.** They affect implementation but don't block writing the spec.
- **Behavior section has 2 examples.** More than the simple example (1) but bounded - only for the most non-obvious AC.

## What Makes This Spec Work for Complex Cases

1. **Multi-actor table is concrete.** Each actor has a distinct role and interaction; not generic.
2. **Non-goals call out plausible-but-excluded scope.** Multi-round reviews and code review are likely "next things someone would ask for" - explicitly out.
3. **Revisions audit-trail is complete.** Six months later, anyone can see why this spec is shaped the way it is.
4. **Open Questions have substance.** Each one names the tradeoff and suggests a lean - "decide later" with context, not "we don't know."
5. **AC are discoverable from the Task Summary.** A reviewer scanning the spec sees fulfillment state without reading the full body.
