# plab-release-plan

**Version:** 1.6.0
**Source:** [`skills/plab-release-plan/`](../../../skills/plab-release-plan/)

Manage a version-scoped release plan. Owns the release folder, the `_unassigned/` -> release promotion ceremony, the aggregation table, hygiene gates, and the doc-update checklist that gates the tag.

---

## Getting Started

### Quick Start

Create a new release:

```
/plab-release-plan --create v1.5.0
```

Move work into it:

```
/plab-release-plan --promote --from _unassigned --to v1.5.0 S-07 S-09
```

Check readiness:

```
/plab-release-plan --gate v1.5.0
```

### Five Subcommands

| Subcommand | What it does |
|-----------|--------------|
| `--create vX.Y.Z` | Start a new release: create the folder, write `plan.md` inside it, scaffold the doc-update checklist and hygiene gates section |
| `--promote --from _unassigned --to vX.Y.Z S-NN ...` | Move named per-effort folders into the release; update spec frontmatter (`target-release`, `linked-release`); refresh aggregation |
| `--demote --from vX.Y.Z [--to _unassigned] S-NN` | Reverse promote: move the effort folder back, clear spec frontmatter. `--to` defaults to `_unassigned` |
| `--update vX.Y.Z` | Regenerate the aggregation table + dynamic frontmatter (`spec-count`, `plan-count`, `checklist-complete`) by walking the folder |
| `--gate vX.Y.Z` | Read-only readiness report. Walks the 5 hygiene gates + counts the doc-update checklist. Reports pass/fail per gate |

### Invocation

**Manual only from 1.6.0, provisionally.** The skill ships with `disable-model-invocation: true` again, so it never fires on its own and runs only when you type `/plab-release-plan` with a subcommand. It shipped with the flag through 1.3.0, was auto-discoverable from 1.4.0 to 1.5.1, and regained it by the maintainer's ruling of 2026-10-17.

The skill has never been run in this repository. It was built for release plans numbered in advance, while versions are now assigned at ship time, and its readiness gate (f) cites two files this repository does not have. A review of the wider release plan will decide whether the flag comes off again or the skill is retired.

Cutting a release is a deliberate act performed on a handful of days. A skill that reshapes release folders should not be reachable by an ambiguous phrase match mid-conversation.

## The Release Folder

The release folder is **self-contained**. The plan document lives inside its own folder, alongside per-effort subfolders as peers.

```
docs/internal/release-plans/
├── plan_v1.4.0/                                  # release folder
│   ├── plan_v1.4.0.md                            # the release plan document
│   ├── S-07_retry-policy/                        # per-effort folder
│   │   ├── spec.md
│   │   └── implementation-plan.md
│   └── S-05_config-loader-refactor/
│       ├── spec.md
│       └── implementation-plan.md
├── _unassigned/                                  # pre-release home, per-effort shape
│   └── S-09_effort-intake/
│       └── spec.md
└── release-checklist.yaml                        # optional, project-level checklist extensions
```

The release is the **closure boundary**: when `v1.4.0` ships, every artifact under `plan_v1.4.0/` is frozen together as a coherent unit. The skill never modifies a released folder.

## The Aggregation Table

Auto-generated by `--update` from the folder walk. Never hand-edit rows; if you find yourself wanting to, run `--update` instead.

```markdown
| id | title | spec-status | plan-status | AC-coverage | has-plan? |
|----|-------|-------------|-------------|-------------|-----------|
| S-07 | Retry policy with backoff | committed | executing | complete | yes |
| S-05 | Config loader refactor | draft | (none) | (none) | no |
```

The skill walks `plan_NN_<slug>/<id>_<slug>/` subfolders, reads each effort's `spec.md` and `implementation-plan.md` frontmatter, and reports facts. No inference.

## The Five Hygiene Gates

Gates block tagging. `--gate` reports current pass/fail. Defined in [`references/hygiene-gates.md`](../../../skills/plab-release-plan/references/hygiene-gates.md):

| Gate | Condition |
|------|-----------|
| **(a) Spec status** | Every effort's `spec.md` has `status: committed` or `fulfilled` (no `draft`) |
| **(b) Coupled plan** | Every effort folder has an `implementation-plan.md`, or is waived in `gate-waivers` |
| **(c) AC coverage** | Every `implementation-plan.md` has `ac-coverage: complete` |
| **(d) Phases done** | Every plan's completion table shows every phase `Done` |
| **(e) Staleness** | No `spec.md` edited after its sibling `implementation-plan.md` |

Plus the **doc-update checklist** (next section).

### Gate waivers

Genuine exceptions get explicit waivers in the release plan's frontmatter:

```yaml
gate-waivers:
  - id: S-12
    gate: b
    reason: "One-line README fix; no implementation plan needed."
```

Waivers require a reason. `--gate` shows waived items as `PASS (waived: <reason>)` so they remain visible rather than silent.

## The Doc-Update Checklist

A table in `plan.md` with checkboxes. Every box must be checked before the tag.

### Built-in defaults

| Doc | Update |
|-----|--------|
| `CHANGELOG.md` | Move items from [Unreleased] to vX.Y.Z |
| `README.md` | Bump version references |
| `AGENTS.md` | Reflect new or renamed skills |
| `docs/skills/README.md` | Sync per-skill version table |
| `skills/*/HISTORY.md` | Append the version's changes per affected skill |
| `.claude-plugin/plugin.json` | Bump plugin `version` |
| `skills/*/SKILL.md` | Bump per-skill `version` frontmatter per affected skill |
| Git tag `vX.Y.Z` | Create the annotated tag |

### Project-level extensions

Optional `docs/internal/release-plans/release-checklist.yaml` adds project-specific items:

```yaml
# Optional. Skill applies built-in defaults plus anything listed here.
add:
  - doc: "marketplace.json"
    update: "Description text references new version"
  - doc: ".github/workflows/release.yml"
    update: "Bump version variable if used"
```

See [`references/checklist-extension.md`](../../../skills/plab-release-plan/references/checklist-extension.md) for the schema.

### Per-release tweaks

The generated checklist in `plan.md` is hand-editable. If a specific release needs a one-off item ("update migration guide for breaking change in v1.4.0"), edit the file directly. The next `--update` does not clobber manual additions.

## Output Shape

`--create` produces a self-contained release folder `docs/internal/release-plans/plan_NN_<slug>/` holding `plan.md` plus per-effort `<id>_<slug>/` subfolders as peers. The plan document includes (in order):

| Section / Element | Purpose |
|-------------------|---------|
| Frontmatter | `type: release-plan` metadata: version, status, dates, `includes:` effort list, and `spec-count` / `plan-count` / `checklist-complete` fields computed by `--update` |
| `## Theme` | One-line release theme (from `--theme` or defaulted) |
| `## Context` | Optional maintainer-authored note on why this release exists |
| `## Aggregation` | Auto-generated table (one row per effort folder: id, title, spec-status, plan-status, AC-coverage, has-plan?). Never hand-edited |
| `## Hygiene Gates` | The five default tag-blocking gates (spec status, coupled plan, AC coverage, phases done, staleness) with a Status column updated by `--gate` |
| `## Doc-Update Checklist` | Checkbox table of docs to update before the tag: built-in defaults plus any `release-checklist.yaml` extensions |
| `## Open Questions / Decisions` | First-class maintainer-authored section for release-planning decisions and open questions, following the decisions-section standard |
| `## Notes` | Maintainer-authored catch-all for anything that doesn't fit elsewhere |

The aggregation, gate Status, and dynamic frontmatter are generated by walking the folder; theme, context, decisions, and notes are maintainer-authored and left untouched by `--update`. Full structural contract in [`references/plan-template.md`](../../../skills/plab-release-plan/references/plan-template.md).

```
Doc-update checklist: 8 items, all unchecked.
Hygiene gates: N/A (no efforts in scope).

Next: run /plab-release-plan --promote to bring efforts in scope.
```

### Example 2: Promote work in

```
$ /plab-release-plan --promote --from _unassigned --to v1.5.0 S-07 S-05

Promoting S-07 (retry policy):
  + Move folder: _unassigned/S-07_retry-policy/
              -> plan_v1.5.0/S-07_retry-policy/
              (contains: spec.md, implementation-plan.md)
  + Update spec.md frontmatter: target-release = v1.5.0,
              linked-release = docs/internal/release-plans/plan_v1.5.0/plan_v1.5.0.md

Promoting S-05 (Config loader refactor):
  + Move folder: _unassigned/S-05_config-loader-refactor/
              -> plan_v1.5.0/S-05_config-loader-refactor/
              (contains: spec.md only; no implementation plan yet)
  + Update spec.md frontmatter

Updated: plan_v1.5.0.md aggregation table now shows 2 efforts.
```

### Example 3: Refuse to ship before ready

```
$ /plab-release-plan --gate v1.5.0

Aggregation: 2 efforts, 1 plan, 12 AC across the release.

Hygiene gates:
  (a) spec status committed/fulfilled .......... FAIL (S-05 is draft)
  (b) every effort has coupled plan ............ FAIL (S-05 has no plan; not waived)
  (c) implementation plan ac-coverage complete . PASS (1 of 1)
  (d) every phase Done ......................... FAIL (S-07: P3 In progress, P4 Not started)
  (e) no spec edited after plan ................ PASS

Doc-update checklist: 0 of 8 checked.

NOT READY TO SHIP. Resolve the 3 failed gates and check the 8 doc-update items,
then re-run --gate.
```

## The Promote / Demote Atomicity Contract

Each promote or demote is atomic at the folder level: either the whole folder move + frontmatter updates complete, or the operation fails with no partial state. Details in [`references/promote-demote.md`](../../../skills/plab-release-plan/references/promote-demote.md).

On a successful promote:

1. The source folder no longer exists in `_unassigned/`
2. The destination folder exists in `plan_NN_<slug>/` with all original contents
3. The spec's `target-release` and `linked-release` frontmatter is updated
4. The implementation plan's `linked-release` is updated (if it exists)
5. The release plan's `includes:` list grows

On a failure, the source folder is preserved with original contents; no half-move state.

## Hard Constraints

1. **AC live in specs, not the release plan.** If asked to add AC, refuse and redirect to `/plab-spec --revise`.
2. **Atomicity of promote/demote.** Move + frontmatter updates either both complete or both fail. No partial state.
3. **Aggregation is generated, not authored.** `--update` regenerates the table; never hand-edit rows.
4. **Status flows up from evidence.** Never auto-set `status: released`. The skill reports readiness; the human acts on it.
5. **Checklist is a gate, not a reminder.** `--gate` reports unchecked items as FAIL. Tag time requires every box checked.
6. **Folder is self-contained.** `plan.md` lives INSIDE `plan_NN_<slug>/`, not as a sibling.

## Tips

- **Run `--gate` often.** It's read-only, fast, and tells you exactly what's between you and ready.
- **Promote drafts.** Per D1: you can promote a spec while it's still `draft`. The gate at tag time catches it. This lets you scope work into a release before the AC are fully frozen.
- **Use waivers sparingly.** Each `gate-waiver` is an explicit decision to ship despite a missing safeguard. Document why.
- **`--update` is safe to run anytime.** It only regenerates the dynamic sections (aggregation + dynamic frontmatter fields); maintainer-authored sections (theme, decisions, checklist text) are untouched.
- **The doc-update checklist is the most-deferrable part of a release.** Most people leave it for the very end. If you're not sure something is ready to ship, work the checklist first - it surfaces dependencies on other docs.
